# Migration and upgrades

## Versioning policy

MispFleet follows semantic versioning. During `0.x` the public API may change
between minor releases; from `1.0.0` the documented public API — the
`mispfleet` top-level exports, the CLI command tree, exit codes and the
configuration schema — is the stability contract.

Breaking changes are announced in `CHANGELOG.md` with a migration note, and
whenever practical the previous form keeps working for one minor release with
a deprecation warning on the `mispfleet` logger.

## Upgrading the package

```bash
pip install --upgrade mispfleet
mispfleet version
mispfleet config validate
```

`config validate` is the fastest post-upgrade check: it reports unknown keys,
unresolvable credentials and servers that no longer satisfy the security
constraints.

## Configuration schema

The configuration carries an explicit `version` key:

```yaml
version: 1
```

MispFleet refuses to load a configuration whose version it does not support
(exit code 3) rather than guessing. When a future release introduces
`version: 2`, the release notes document the field-by-field migration and
`mispfleet config validate` names every key that must change.

Configuration models reject unknown keys (`extra: forbid`) in `defaults`,
`state`, `security` and policy specifications. A typo is an error at load
time, not a setting that is silently ignored.

### Settings added after the initial release

| Key | Default | Notes |
| --- | ------- | ----- |
| `security.forbid_insecure_tls` | `false` | when `true`, `verify_tls: false` and `--no-verify-tls` are refused |
| `state.capability_ttl_seconds` | `3600` | lifetime of cached server capabilities |
| `defaults.http2` / per-server `http2` | `false` | needs the `http2` extra |
| `defaults.keepalive_expiry`, `max_keepalive_connections` | unset | httpx pool defaults apply when unset |
| `defaults.max_response_bytes` | `50000000` | response-size guard |

All of them are optional; existing configuration files keep working unchanged.

## State schema

The state backend (SQLite by default, MariaDB optionally) creates its schema
with `CREATE TABLE IF NOT EXISTS` on `initialize()`, so upgrades that add a
table — such as the `capabilities` cache — apply automatically the next time
a command touches state. No manual migration step is required.

Tables in use: `checkpoints`, `operations`, `capabilities`. If you ever need
to start over, deleting the state file only loses resumable checkpoints, the
local audit trail and the capability cache; nothing on the MISP servers is
affected.

```bash
mispfleet state info            # where state lives and what it holds
mispfleet state prune --older-than 30d
```

## Plan files across versions

Copy plans are portable JSON documents that record the source fingerprint,
both server names and the policy used. Applying a plan re-validates all of it,
so a plan generated by an older version is either applied safely or rejected
with `StalePlanError` / `UnsafePlanError` — never applied blindly. Regenerate
plans after upgrading rather than reusing stale ones.

## Upgrading MISP servers

Behavior follows discovered capabilities, not version strings, so a server
upgrade is usually transparent. Two things are worth doing afterwards:

```bash
mispfleet servers capabilities --all --refresh
mispfleet servers versions --all
```

`--refresh` bypasses the capability cache and re-probes, so newly available
features are picked up immediately instead of after the TTL expires. See
[Compatibility](compatibility.md) for the tested MISP matrix.
